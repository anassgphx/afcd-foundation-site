# ADR 0001 — AFCD Studio architecture

Status: accepted for Phase 1–2 (local development). Production hosting is an open decision (see "Open decisions").
Date: 2026-11-22

## Context: what the codebase actually is

The audit of the repository found:

| Area | Finding |
|---|---|
| Framework | **Not Astro.** Plain static HTML. `src/content.py` (Python 3, stdlib only) writes page sources to `src/pages/*.html`; `build.mjs` (Node) wraps them in `src/partials/{head,header,footer}.html` and writes the public HTML files to the repository root. |
| Styles | Tailwind CSS 3.4 compiled from `input.css` to `assets/styles.css`; Tailwind scans `src/**/*.html` and `assets/main.js`. Design tokens and component classes live in `input.css`. |
| Routes | 20 flat `*.html` routes (`index.html`, `about.html`, `project-*.html`, pillar pages, `404.html`, …). `sitemap.xml` and `robots.txt` are generated by `build.mjs`. |
| Interactivity | One vanilla JS file, `assets/main.js` (menus, sliders, filters, form checks, animations). |
| Content | Projects, pillars, objectives, beneficiaries, news and partners are Python literals in `src/content.py`. Homepage content is hand-written in `src/pages/index.html`. |
| Images | Three images in `assets/img`; the rest are grey placeholders. |
| Forms | Contact and newsletter forms validate in the browser only. Nothing is sent. |
| Hosting | GitHub Pages (static) for the preview; production domain `afcdfoundation.org` not yet switched. |
| Backend / DB | None. |
| Local tooling | Node 26, npm 11, Python 3. No PostgreSQL, Docker or Homebrew installed. |

## Decision

### 1. Keep the public site and its build pipeline
The public website is not migrated to another framework. AFCD Studio **publishes into the existing pipeline**: it exports published content as JSON (`src/data/studio/*.json`), then runs `content.py` and `build.mjs` exactly as a developer would. The design, URLs and SEO output of the existing generator are preserved, and the public site stays pure static HTML (fast, cacheable, no runtime API calls).

### 2. Modular monolith in TypeScript, under `studio/`
One Node process serves the JSON API (`/studio/api/*`), the admin app (`/studio/*`) and previews (`/studio/preview/*`). Modules have their own routes, services and validation (`auth`, `rbac`, `audit`, `projects`, `media`, `workflow`, `publish`, `dashboard`). No microservices.

| Concern | Choice | Why |
|---|---|---|
| HTTP framework | **Hono** (+ `@hono/node-server`) | Small, maintained, typed, runs on Node and edge runtimes, so hosting stays open. Fastify/NestJS were heavier than this monolith needs. |
| Database | **PostgreSQL** | As required. |
| Local PostgreSQL | **PGlite** (PostgreSQL compiled to WASM, in-process) | No system install needed; data persists in `studio/.data/pg`. Same SQL and migrations as a server. |
| Production PostgreSQL | `pg` (node-postgres) via `DATABASE_URL` | Selected automatically when `DATABASE_URL` is set. |
| ORM / migrations | **Drizzle ORM + drizzle-kit** | Typed schema in TS, plain SQL migrations committed to the repo, supports both PGlite and node-postgres. Prisma's engine binaries are heavier and do not run on PGlite. |
| Validation | **Zod**, enforced on the server for every write | |
| Passwords | **Argon2id** via `@node-rs/argon2` | Maintained native binding. No custom crypto. |
| Sessions | Server-side sessions: 32-byte random token in an `HttpOnly; SameSite=Strict` cookie, only the SHA-256 of the token stored in the database (the pattern documented by the Lucia / Copenhagen Book project). Sliding expiry, revocable. | Standard session management built from Node's `crypto`, not a new protocol. MFA (TOTP) is planned for Phase 7 for privileged roles. |
| CSRF | `SameSite=Strict` cookie **plus** Origin check **plus** a per-session CSRF token header on every state-changing request. | |
| Images | **sharp**: validates real image type, strips metadata, writes WebP derivatives (480/960/1600) and keeps the original. | |
| Admin UI | **React + Vite** single-page app, served by the same process | The visual page builder needs rich client state. |
| Background jobs | Phase 1–2: in-process job runner with a database-backed `jobs` table (status, attempts, idempotency key, last error) and a single build lock. | Enough for one instance; can move to `pg-boss` on PostgreSQL later without changing callers. |
| Tests | Vitest (unit, API authorization, workflow) against a throwaway in-memory PGlite database. | |

### 3. Content model
Typed relational tables for canonical records (`pillars`, `objectives`, `projects`, `media`) with join tables (`project_pillars`, `project_objectives`, `project_media`). Each project keeps a **working copy** (the editable row) and immutable **revisions** (JSON snapshots). The live site is built only from the revision pointed to by `projects.published_revision_id`, so editors can prepare changes to a published project without touching what is live.

### 4. Workflow
`draft → in_review → (changes_requested | approved) → published → archived`, with `scheduled` added in Phase 5. Every transition is a server-side state-machine check plus a permission check, runs in a transaction and writes an immutable `audit_log` row.

### 5. Publishing (the delivery contract)
1. Take the build lock.
2. Export published revisions (plus the one being published) to `src/data/studio/projects.json`, copy approved media derivatives to `assets/media/`.
3. Run `python3 -I src/content.py` and `npm run build` in the site root.
4. **Verify**: the project's HTML file exists and contains `data-studio-rev="<revision id>"`; listing and pillar pages contain the project.
5. Only then commit the status change to `published` and record a successful `publish_jobs` row. Any failure keeps the previous live version and records the error, which the dashboard shows.

### 6. Preview
Previews run the same Python template and build wrapper into an isolated `studio/.preview/<token>/` directory (never the public root), served only to signed-in users with `noindex`.

## Security notes
- Every API route checks the session and a named permission on the server; the UI hides actions too, but is not the control.
- Uploads: size limit, allow-list of image types checked by decoding with sharp, random file names, served from a dedicated path with `X-Content-Type-Options: nosniff`.
- No user-supplied HTML, CSS or JS reaches the public site; rich text fields are plain text with paragraphs in Phase 2.
- Secrets come from environment variables (`studio/.env`, never committed). No secret is hardcoded.
- Private institutional identifiers (tax ID, ICE, CNSS, registration number, personal contacts) are not part of any public model.

## Open decisions (need AFCD)
1. **Production hosting.** GitHub Pages cannot run the Studio. Options: (a) a small Node host (e.g. Render, Fly.io, a VPS) with managed PostgreSQL, where publishing commits the rebuilt site to the repository and GitHub Pages redeploys; (b) the same host also serves the public site. Both need credentials and a deployment authorization.
2. **Media storage in production**: local disk is fine for one server; S3-compatible object storage is recommended once hosted.
3. **Email provider** for notifications (Phase 5).

## Phase plan
1. Foundation: schema, migrations, auth, RBAC, audit, admin shell, dashboard. **(this delivery)**
2. Projects + media + workflow + preview + publish to the real site. **(this delivery)**
3. Visual page builder (blocks, inspector, responsive preview, homepage).
4. Pillars, objectives, news, partners as editable modules.
5. Opportunities, forms and submissions, scheduling, notifications.
6. SEO studio, localization (EN/FR/AR with RTL), analytics.
7. Hardening: MFA, rate limits per route, backups and restore tests, monitoring, deployment docs.
